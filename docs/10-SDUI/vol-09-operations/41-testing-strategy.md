## 41.1 Testing Philosophy

AwoERP follows a risk-weighted testing strategy. Not all code has the same risk profile:

- **Authorization logic:** A bug here leaks data across tenants. Testing is exhaustive: every permission combination, every RLS policy, every field policy.
- **Offline queue / conflict resolution:** A bug here loses user data. Every queue and conflict scenario has a test.
- **SDUI compilation:** A bug here corrupts every user's UI. Compilation output is snapshot-tested.
- **Payment and financial mutations:** Every mutation is tested against the exact business rules, including boundary conditions.
- **UI layout and styling:** Moderate risk. Visual regression tests catch the grossest regressions; pixel perfection is not the standard.

The goal is confidence, not coverage percentage. 100% line coverage with poor test cases is worse than 70% coverage with high-quality tests.

## 41.2 Test Pyramid

```
        ┌────────────────────────────────┐
        │       E2E Tests (Playwright)   │  ~100 scenarios
        │       Mobile E2E (Detox)       │  ~50 scenarios
        └──────────────────────────────┬─┘
                                        │ slow, expensive, high confidence
        ┌───────────────────────────────┴────────────────────────────┐
        │          Integration Tests                                  │  ~800 tests
        │  (API + DB, SDUI compilation, offline queue, auth flows)   │
        └────────────────────────────────────────────────────────────┘
                                        │ medium speed, real dependencies
        ┌───────────────────────────────┴────────────────────────────┐
        │              Unit Tests                                     │  ~3,000 tests
        │     (business logic, validation, formatters, DSL parsing)  │
        └────────────────────────────────────────────────────────────┘
                                        │ fast, isolated, cheapest to run
```

| Layer | Runtime Target | Runs In CI |
|-------|---------------|------------|
| Unit | < 30 seconds | Every PR |
| Integration | < 5 minutes | Every PR |
| E2E | < 20 minutes | Every PR (parallelized) |
| Visual regression | < 10 minutes | Every PR |
| Performance | < 30 minutes | Daily + release |
| Security | < 30 minutes | Daily + release |

## 41.3 Unit Tests

### 41.3.1 Go Unit Tests

Go unit tests follow standard Go conventions. Key rules:
- Table-driven tests for any function with more than two meaningful inputs
- No database, Redis, or network calls in unit tests
- Mocks generated by `mockery` from interfaces

```go
func TestFlagEvaluator_Evaluate(t *testing.T) {
    tests := []struct {
        name     string
        flag     FeatureFlag
        context  EvalContext
        expected FlagValue
    }{
        {
            name: "user override takes precedence",
            flag: FeatureFlag{
                Key:     "new_dashboard",
                Default: BoolValue(false),
                TenantOverride: BoolValue(true),
            },
            context: EvalContext{
                UserID:   "user-1",
                TenantID: "tenant-1",
                UserOverrides: map[string]FlagValue{
                    "new_dashboard": BoolValue(false),
                },
            },
            expected: BoolValue(false), // User override beats tenant override
        },
        {
            name: "percentage rollout: in rollout",
            flag: FeatureFlag{
                Key:     "beta_feature",
                Default: BoolValue(false),
                RolloutRules: []RolloutRule{{Percentage: 50, Value: BoolValue(true)}},
            },
            context: EvalContext{TenantID: "tenant-always-in-50pct"},
            // Precomputed: FNV32a("tenant-always-in-50pct" + salt) % 100 < 50
            expected: BoolValue(true),
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            evaluator := NewFlagEvaluator()
            result := evaluator.Evaluate(tt.flag, tt.context)
            assert.Equal(t, tt.expected, result)
        })
    }
}
```

### 41.3.2 TypeScript Unit Tests (Jest)

Frontend unit tests cover:
- Patch application logic (`applyPatch`)
- Expression evaluation (`$expr{ }`)
- Binding resolution
- Formatting utilities (currency, date, number)

```typescript
describe('applyPatch', () => {
    it('applies set_props to a specific row', () => {
        const store = buildStore({
            version: 10,
            data: { invoices: { rows: [{ id: 'inv-1', status: 'draft' }] } },
        });

        const result = applyPatch(store, {
            version: 11,
            base_version: 10,
            operations: [{
                op: 'set_props',
                path: '$.data_sources.invoices.rows[id=inv-1]',
                props: { status: 'approved' },
            }],
        });

        expect(result).toBe(true);
        expect(store.data.invoices.rows[0].status).toBe('approved');
        expect(store.version).toBe(11);
    });

    it('returns false on version mismatch', () => {
        const store = buildStore({ version: 10 });
        const result = applyPatch(store, { version: 12, base_version: 11, operations: [] });
        expect(result).toBe(false);
        expect(store.version).toBe(10); // Unchanged
    });
});
```

## 41.4 Integration Tests

### 41.4.1 Test Infrastructure

Integration tests run against:
- A real PostgreSQL instance (Docker container in CI, local Docker in development)
- A real Redis instance (Docker container)
- Test doubles for OpenFGA, Temporal, and external services

```go
func TestMain(m *testing.M) {
```

### 41.4.2 RLS Integration Tests

RLS policies are integration-tested exhaustively. Tests verify that a query run as tenant A cannot return tenant B's data:

```go
func TestRLS_TenantIsolation(t *testing.T) {
    // Create two tenants with invoices
    tenantA := createTestTenant(t)
    tenantB := createTestTenant(t)
    invoiceA := createTestInvoice(t, tenantA.ID)
    createTestInvoice(t, tenantB.ID)

    // Query as tenant A
    db := testDBWithContext(t, tenantA.ID, testUserID)
    var invoices []Invoice
    err := db.Select(&invoices, "SELECT * FROM invoices")
    require.NoError(t, err)

    // Should only see tenant A's invoice
    require.Len(t, invoices, 1)
    assert.Equal(t, invoiceA.ID, invoices[0].ID)
}
```

### 41.4.3 Authorization Integration Tests

```go
func TestAuthorization_FieldPolicy(t *testing.T) {
    // User with "viewer" role should not see amount field
    surface := compileSurface(t, "invoice_detail", viewerRoleSet)

    // Find the amount field in the compiled surface
    amountField := findComponent(surface, "field_invoice_amount")

    surface = compileSurface(t, "invoice_detail", approverRoleSet)
```

## 41.5 End-to-End Tests

### 41.5.1 Web E2E (Playwright)

E2E tests run against a real deployed environment (the staging environment in CI):

```typescript
test.describe('Invoice approval workflow', () => {
    test('approver can approve a pending invoice', async ({ page }) => {
        await loginAs(page, 'approver@test-tenant.com');
        await page.goto('/invoices?status=pending_approval');

        // Wait for surface to be ready
        await page.waitForSelector('[data-testid="invoice-table"]');

        // Click the first pending invoice
        await page.click('[data-testid="invoice-row"]:first-child');
        await page.waitForSelector('[data-testid="surface-invoice-detail"]');

        // Click approve
        await page.click('[data-testid="btn-action-approve"]');
        await page.waitForSelector('[data-testid="confirm-dialog"]');
        await page.click('[data-testid="btn-confirm"]');

        // Wait for success
        await expect(page.locator('[data-testid="status-badge"]')).toHaveText('Approved');
    });
});
```

### 41.5.2 Mobile E2E (Detox)

Mobile E2E tests cover the offline scenario in particular:

```typescript
// Detox test
describe('Offline invoice creation', () => {
    it('queues invoice creation when offline and replays on reconnect', async () => {
        await device.setNetworkCondition('offline');

        await element(by.id('btn-create-invoice')).tap();
        await element(by.id('input-vendor')).typeText('Test Vendor');
        await element(by.id('input-amount')).typeText('50000');
        await element(by.id('btn-save-draft')).tap();

        // Should show queued indicator
        await expect(element(by.id('offline-queue-badge'))).toBeVisible();
        await expect(element(by.id('offline-queue-badge'))).toHaveText('1');

        // Restore connectivity
        await device.setNetworkCondition('online');

        // Should sync and show success
        await waitFor(element(by.id('offline-queue-badge'))).toNotExist().withTimeout(30000);
        await expect(element(by.id('toast-sync-success'))).toBeVisible();
    });
});
```

## 41.6 SDUI Surface Tests

### 41.6.1 Compilation Snapshot Tests

The surface compiler's output is snapshot-tested. For each surface definition and role combination, the expected compiled output is stored as a JSON snapshot:

```go
func TestSurfaceCompiler_InvoiceList(t *testing.T) {
    compiler := buildTestCompiler(t)
    ctx := buildTestContext("en-KE", approverRoleSet, defaultFlags)

    result, err := compiler.Compile(ctx, "invoice_list")
    require.NoError(t, err)

    // Golden file test: compare to expected snapshot
    goldenFile := "testdata/invoice_list_approver_en-ke.json"
    if *update {
        writeJSON(t, goldenFile, result)
    } else {
        expected := readJSON(t, goldenFile)
        assert.JSONEq(t, expected, marshalJSON(t, result))
    }
}
```

Update golden files by running `go test -update`. Snapshots are committed to the repository. Any change to the compiled output for an existing surface requires a deliberate golden file update, making accidental regressions visible in the PR diff.

### 41.6.2 Role Permutation Tests

For each surface, the test suite compiles the surface for every defined role and verifies:
- No components with `requires_permission` remain for roles that lack the permission
- At least one component is rendered for all valid roles (a surface that compiles to empty for a valid role is a bug)

## 41.7 Visual Regression Tests

### 41.7.1 Playwright Visual Comparisons

```typescript
test('invoice list surface — visual snapshot', async ({ page }) => {
    await loginAs(page, 'approver@test-tenant.com');
    await page.goto('/invoices');
    await page.waitForSelector('[data-testid="invoice-table"]');

    // Wait for network idle (data loaded)
    await page.waitForLoadState('networkidle');

    await expect(page).toHaveScreenshot('invoice-list-approver.png', {
        threshold: 0.02,   // 2% pixel difference tolerance
        maxDiffPixels: 100,
    });
});
```

Visual snapshots are taken for:
- Every surface in LTR (en-KE)
- Key surfaces in RTL (ar-EG)
- Responsive breakpoints (375px mobile, 768px tablet, 1280px desktop)
- Dark mode (if supported)

### 41.7.2 Snapshot Update Process

Visual regression failures require a human decision: is this a regression (something broke) or a deliberate change (new design)? The CI workflow:

1. Run visual tests
2. On failure: upload diff images to the PR as artifacts
3. Engineer reviews: if intentional, run `pnpm test:visual --update-snapshots` and commit new baselines
4. New baselines must be reviewed and approved in the PR

## 41.8 Performance Tests

### 41.8.1 Load Tests (k6)

Load tests run in the CI pipeline on a dedicated staging environment:

```javascript
// k6 load test: surface load under concurrent users
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
    stages: [
        { duration: '2m', target: 100 },   // Ramp up to 100 users
        { duration: '5m', target: 100 },   // Sustain
        { duration: '2m', target: 0 },     // Ramp down
    ],
    thresholds: {
        http_req_duration: ['p(95)<200', 'p(99)<500'],
        http_req_failed: ['rate<0.01'],
    },
};

export default function () {
    const res = http.get(
        `${BASE_URL}/api/sdui/surfaces/invoice_list`,
        { headers: authHeaders(VU_TOKENS[__VU % VU_TOKENS.length]) }
    );

    check(res, {
        'status is 200 or 304': r => r.status === 200 || r.status === 304,
        'response time < 200ms': r => r.timings.duration < 200,
    });

    sleep(1);
}
```

### 41.8.2 Performance Regression Gate

The performance test results are compared to the baseline. If p95 or p99 latency regresses by more than 10%, the CI pipeline marks the build as failed.

## 41.9 Security Tests

### 41.9.1 OWASP ZAP Scan

Automated OWASP ZAP scans run against the staging environment weekly and before every release:

```bash
docker run -t owasp/zap2docker-stable zap-baseline.py \
    -t https://staging.awoerp.dev \
    -r zap_report.html \
    --hook /zap/auth_hook.py  # Custom hook for JWT auth
```

ZAP findings are classified:
- **High / Critical:** Block release. Must fix before shipping.
- **Medium:** Tracked as issues. Must fix within one sprint.
- **Low / Informational:** Reviewed by the security team; fix or accept.

## 41.10 Test Data Management

### 41.10.1 Test Fixtures

Test fixtures are defined as Go struct factories, not raw SQL:

```go
type InvoiceFixture struct {
    store *Store
}

func (f *InvoiceFixture) Build(opts ...InvoiceOption) *Invoice {
    inv := &Invoice{
        ID:           uuid.New().String(),
        TenantID:     testTenantID,
        VendorID:     testVendorID,
        Amount:       100000,
        CurrencyCode: "KES",
        Status:       "draft",
    }
    for _, opt := range opts {
        opt(inv)
    }
    return inv
}

func (f *InvoiceFixture) Create(t *testing.T, opts ...InvoiceOption) *Invoice {
    inv := f.Build(opts...)
    err := f.store.CreateInvoice(context.Background(), inv)
    require.NoError(t, err)
    t.Cleanup(func() { f.store.DeleteInvoice(context.Background(), inv.ID) })
    return inv
}

// Option pattern for easy customization
func WithStatus(status string) InvoiceOption {
    return func(i *Invoice) { i.Status = status }
}
func WithAmount(amount int64) InvoiceOption {
    return func(i *Invoice) { i.Amount = amount }
}
```

### 41.10.2 Test Tenant Isolation

Every integration test runs in its own tenant. Tests never share tenant state:

```go
func createTestTenant(t *testing.T) *Tenant {
    t.Helper()
    tenant := &Tenant{
        ID:        uuid.New().String(),
        Subdomain: fmt.Sprintf("test-%s", ulid.Make()),
        Name:      "Test Tenant",
        Status:    "active",
    }
    err := testStore.CreateTenant(context.Background(), tenant)
    require.NoError(t, err)
    t.Cleanup(func() {
        // Cascade delete: removes all tenant data including RLS-scoped rows
        testStore.DeleteTenant(context.Background(), tenant.ID)
    })
    return tenant
}
```

### 41.10.3 No Production Data in Tests

Tests never use production data, even anonymized. All test data is synthetic. Seeding test environments with production data (even a backup) is prohibited by the data governance policy.
