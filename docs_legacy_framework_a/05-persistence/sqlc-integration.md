# SQLC Integration

**PERS-014 | Status: Accepted | Stability: Stable**

How SQLC fits into the Awo persistence layer, the boundary between generated queries and the `EntityRepository` interface, and what module authors must know.

---

## 1. What SQLC Does

SQLC is a code generator that reads annotated SQL files and produces type-safe Go functions. Given:

```sql
-- name: GetInvoiceByID :one
SELECT * FROM finance_invoice WHERE id = $1 AND tenant_id = current_tenant_id();
```

SQLC generates:

```go
func (q *Queries) GetInvoiceByID(ctx context.Context, id uuid.UUID) (FinanceInvoice, error)
```

The generated code in `db/sqlc/` is **framework-internal**. Module authors never call SQLC functions directly.

---

## 2. The Layering

```
Module Author Code
        │
        │  uses
        ▼
EntityRepository[T] interface   ← the only persistence interface for modules
        │
        │  implemented by
        ▼
sqlRepository[T]                ← framework-internal implementation
        │
        │  calls
        ▼
db/sqlc/Queries                 ← generated by SQLC from db/queries/*.sql
        │
        │  uses
        ▼
pgx v5 pool                     ← actual PostgreSQL connection
        │  (via PgBouncer, transaction mode)
        ▼
PostgreSQL + RLS
```

Module authors interact only with the top two layers. The SQLC layer is invisible to them.

## 3. SQLC Configuration

File: `sqlc.yaml` at the repository root.

```yaml
version: "2"
sql:
  - engine: "postgresql"
    queries: "db/queries/"
    schema: "db/migration/"
    gen:
      go:
        package: "sqlc"
        out: "db/sqlc"
        emit_interface: true
        emit_json_tags: true
        emit_db_tags: true
        overrides:
          - db_type: "uuid"
            go_type: "github.com/google/uuid.UUID"
          - db_type: "numeric"
            go_type: "github.com/shopspring/decimal.Decimal"
          - db_type: "timestamptz"
            go_type: "time.Time"
          - db_type: "text[]"
            go_type: "[]string"
          - db_type: "jsonb"
            go_type: "map[string]any"
            nullable: true
```

## 4. Query File Organization

SQL query files live in `db/queries/`, one file per entity:

```
db/queries/
    finance_invoice.sql
    finance_customer.sql
    inventory_product.sql
    iam_user.sql
    iam_session.sql
    tenant.sql
    ...
```

Each file contains the annotated queries for that entity:

```sql
-- db/queries/finance_invoice.sql

-- name: GetFinanceInvoice :one
SELECT * FROM finance_invoice
WHERE id = @id
  AND tenant_id = current_tenant_id();

-- name: ListFinanceInvoices :many
SELECT * FROM finance_invoice
WHERE tenant_id = current_tenant_id()
  AND (@status::text IS NULL OR status = @status)
ORDER BY created_at DESC
LIMIT @limit_val OFFSET @offset_val;

-- name: CreateFinanceInvoice :one
INSERT INTO finance_invoice (
    id, tenant_id, number, customer, status, total_kes, created_at, updated_at
) VALUES (
    @id, current_tenant_id(), @number, @customer, @status, @total_kes, NOW(), NOW()
)
RETURNING *;

-- name: UpdateFinanceInvoice :one
UPDATE finance_invoice
SET status     = COALESCE(@status, status),
    total_kes  = COALESCE(@total_kes, total_kes),
    updated_at = NOW()
WHERE id = @id
  AND tenant_id = current_tenant_id()
RETURNING *;

-- name: DeleteFinanceInvoice :exec
DELETE FROM finance_invoice
WHERE id = @id
  AND tenant_id = current_tenant_id();

-- name: CountFinanceInvoices :one
SELECT COUNT(*) FROM finance_invoice
WHERE tenant_id = current_tenant_id()
  AND (@status::text IS NULL OR status = @status);
```

**Notice**: `current_tenant_id()` appears in every query. This is redundant with RLS but is defense-in-depth — even if RLS were accidentally disabled, the query itself would still scope to the current tenant.

## 5. How the Repository Uses SQLC

The framework's `sqlRepository[T]` uses SQLC queries internally and translates the `*filter.Filter` tree into parameterized SQL conditions at runtime.

For standard CRUD, SQLC-generated functions handle the simple cases directly. For dynamic filtering (the `Query` method with arbitrary `*Filter` trees), the repository constructs WHERE clauses using a filter-to-SQL translator, then executes via `pgx` directly (not SQLC — SQLC only handles static queries).

```
EntityRepository.Query(ctx, filter.And(
    filter.Eq("status", "Submitted"),
    filter.Gte("created_at", lastWeek),
))
        │
        ▼
filterToSQL(*Filter) → "WHERE tenant_id = current_tenant_id() AND status = $1 AND created_at >= $2"
                        args = ["Submitted", lastWeek]
        │
        ▼
pgxPool.Query(ctx, builtSQL, args...)
```

For Get-by-ID, CreateOne, UpdateOne, DeleteOne → SQLC-generated functions are used (type-safe, no runtime SQL construction).

For `Query`, `Count`, `Aggregate` with dynamic filters → runtime SQL builder (not SQLC).

## 6. Generated Output Structure

After `sqlc generate`, `db/sqlc/` contains:

```
db/sqlc/
    db.go           ← DBTX interface (works with pgx.Pool or pgx.Tx)
    models.go       ← Go structs matching each table (e.g. FinanceInvoice)
    querier.go      ← Querier interface — all generated method signatures
    query.sql.go    ← Concrete implementations (one file per query file)
```

`querier.go` is the interface that wire-injects into the repository:

```go
// db/sqlc/querier.go (generated, do not edit)
type Querier interface {
    GetFinanceInvoice(ctx context.Context, id uuid.UUID) (FinanceInvoice, error)
    ListFinanceInvoices(ctx context.Context, arg ListFinanceInvoicesParams) ([]FinanceInvoice, error)
    CreateFinanceInvoice(ctx context.Context, arg CreateFinanceInvoiceParams) (FinanceInvoice, error)
    UpdateFinanceInvoice(ctx context.Context, arg UpdateFinanceInvoiceParams) (FinanceInvoice, error)
    DeleteFinanceInvoice(ctx context.Context, arg DeleteFinanceInvoiceParams) error
    CountFinanceInvoices(ctx context.Context, arg CountFinanceInvoicesParams) (int64, error)
    // ... 500+ methods
}
```

## 7. What Module Authors Must Know

Module authors **never**:
- Import `db/sqlc` in module code
- Call `Queries` methods directly
- Write raw SQL in hook or handler code

Module authors **always**:
- Use `EntityRepository[T]` methods (`Get`, `Query`, `Create`, `Update`, `Delete`)
- Use `filter.*` constructors for predicates
- Use `QueryOption`s for edge loading

When a module needs a query that does not fit the standard repository interface (e.g., a complex aggregate JOIN across two entities), the correct pattern is a **service function** that composes multiple repository calls — not bypassing to SQLC or raw SQL.

## 8. Querier in Tests

For unit tests, mock the `Querier` interface (not the database):

```go
type mockQuerier struct {
    invoices []sqlc.FinanceInvoice
}

func (m *mockQuerier) GetFinanceInvoice(ctx context.Context, id uuid.UUID) (sqlc.FinanceInvoice, error) {
    for _, inv := range m.invoices {
        if inv.ID == id {
            return inv, nil
        }
    }
    return sqlc.FinanceInvoice{}, pgx.ErrNoRows
}
// ... implement other methods
```

For integration tests, use a real PostgreSQL instance — not the mock. See Testing Guidelines in CLAUDE.md.
