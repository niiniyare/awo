# System Entities

**PERS-003 | Status: Accepted | Stability: Frozen**

System entities are entities whose records are stored in typed SQL columns. This document specifies when to use system entities, their schema conventions, migration requirements, and mandatory system entity declarations.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, RECOMMENDED, MAY, and OPTIONAL are interpreted per RFC 2119.

---

## 1. When to Use System Entities

Declare `StorageModel: entity.SystemEntity` when ANY of the following conditions is true:

| Condition | Reason |
|---|---|
| Entity participates in financial calculations | `numeric(20,4)` and SQL constraints required |
| Entity participates in inventory accounting | SQL quantity constraints required |
| Entity is IAM data (users, sessions, roles) | JSONB corruption risk unacceptable for auth data |
| Entity is accessed before per-tenant schemas load | Platform-scoped tables cannot use per-tenant JSONB |
| Write frequency exceeds hundreds per second | SQL rows are faster than JSONB for high-write workloads |
| Fields require FK constraints to other system entity PKs | FK constraints work only on typed columns |

When none of the above conditions apply, use [Custom Entity](custom-entities.md) storage.

---

## 2. Mandatory System Entities

The following entities MUST be declared as system entities. This is enforced by the Entity Registry at compilation:

| Entity Name | Reason |
|---|---|
| `iam_user` | Auth data; JSONB corruption risk unacceptable |
| `iam_session` | Session tokens; performance-critical; auth integrity |
| `iam_role` | RBAC data; must be consistent |
| `platform_tenant` | Platform identity; loaded before per-tenant schemas |
| `finance_ledger_entry` | Double-entry; SQL numeric constraints required |
| `finance_journal_entry` | Double-entry; debit/credit balance at DB level |
| `finance_payment` | Financial transaction; SQL constraints + audit triggers |
| `finance_tax_entry` | KRA eTIMS record; regulatory compliance |
| `inventory_stock_move` | Inventory accounting; SQL quantity constraints |

Adding new entities to this mandatory list requires an ADR.

## 3. Schema Conventions

Every system entity table follows this schema pattern:

```sql
CREATE TABLE finance_invoice (
    -- System columns (generated by framework; do not declare in FieldDef)
    id           uuid        NOT NULL DEFAULT gen_random_uuid(),
    tenant_id    uuid        NOT NULL REFERENCES tenants(id),
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    created_by   uuid,
    version      bigint      NOT NULL DEFAULT 1,
    custom_fields jsonb      NOT NULL DEFAULT '{}',

    -- Declared fields
    number       varchar(64) UNIQUE,
    customer_id  uuid        REFERENCES crm_customer(id),
    status       varchar(32) NOT NULL DEFAULT 'Draft'
                             CHECK (status IN ('Draft','Submitted','Approved','Paid','Cancelled')),
    total_kes    numeric(20,4) NOT NULL,
    due_date     date,
    notes        text,

    PRIMARY KEY (id)
);

-- RLS (mandatory for all tenant-scoped tables)
ALTER TABLE finance_invoice ENABLE ROW LEVEL SECURITY;
ALTER TABLE finance_invoice FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON finance_invoice
    USING (tenant_id = current_tenant_id());

-- Indexes
CREATE INDEX idx_finance_invoice_tenant ON finance_invoice(tenant_id);
CREATE INDEX idx_finance_invoice_customer ON finance_invoice(customer_id);
CREATE INDEX idx_finance_invoice_status ON finance_invoice(status);
CREATE INDEX idx_finance_invoice_custom_fields ON finance_invoice USING GIN(custom_fields);
```

### Conventions

1. **RLS block is mandatory** — every tenant-scoped system entity table MUST have the three-line RLS block. Global tables (not tenant-scoped) omit this block.
2. **`updated_at` trigger** — the store layer updates `updated_at` on every mutation. A database trigger is not required if the store layer reliably does this; a trigger provides defense-in-depth.
3. **`version` column** — present on all system entities for optimistic locking.
4. **`custom_fields` column** — present on all system entities for runtime custom field additions.
5. **GIN index on `custom_fields`** — always present.
6. **Tenant FK index** — `idx_{entity}_tenant` always present for RLS filter performance.

## 4. Migration Requirements

Every new system entity table requires a migration pair:

**`YYYYMMDDHHMMSS_create_finance_invoice.up.sql`**
```sql
CREATE TABLE finance_invoice (
    -- ... as above
);

ALTER TABLE finance_invoice ENABLE ROW LEVEL SECURITY;
ALTER TABLE finance_invoice FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON finance_invoice
    USING (tenant_id = current_tenant_id());

CREATE INDEX idx_finance_invoice_tenant ON finance_invoice(tenant_id);
-- ... additional indexes
```

**`YYYYMMDDHHMMSS_create_finance_invoice.down.sql`**
```sql
DROP TABLE IF EXISTS finance_invoice;
```

Migrations are append-only. See [LAW-012](../02-architecture/laws.md#law-012-migrations-are-append-only) and [Migrations](../14-operations/migrations.md).

## 5. Index Strategy

| Column type | Index type | When |
|---|---|---|
| `tenant_id` | B-tree | Always (FK + RLS performance) |
| FK columns (`customer_id`, etc.) | B-tree | Always |
| Status / Select fields | B-tree | When used in frequent WHERE clauses |
| `custom_fields` | GIN | Always |
| `Data` fields with `Searchable: true` | GIN (trgm) | When declared in FieldDef |
| New production indexes | `CONCURRENTLY` | Always (avoids table lock) |

```sql
-- Production index addition (zero-downtime)
CREATE INDEX CONCURRENTLY idx_finance_invoice_due_date ON finance_invoice(due_date);
```

## 6. Select Constraint Pattern

For `Select` fields, declare the `CHECK` constraint inline with the column:

```sql
status varchar(32) NOT NULL DEFAULT 'Draft'
       CHECK (status IN ('Draft', 'Submitted', 'Approved', 'Paid', 'Cancelled')),
```

When options change (adding a new status), write a new migration that drops the old constraint and adds the new one:

```sql
ALTER TABLE finance_invoice
    DROP CONSTRAINT finance_invoice_status_check,
    ADD CONSTRAINT finance_invoice_status_check
        CHECK (status IN ('Draft', 'Submitted', 'Approved', 'Paid', 'Cancelled', 'Disputed'));
```

---

## 7. Currency Column Pattern

All monetary fields use `numeric(20,4)`:

```sql
total_kes    numeric(20,4) NOT NULL,
tax_amount   numeric(20,4) NOT NULL DEFAULT 0,
paid_amount  numeric(20,4) NOT NULL DEFAULT 0,
```

Never use `float`, `double precision`, or `money` for monetary values. See [INV-008](../02-architecture/invariants.md#inv-008-all-monetary-arithmetic-uses-exact-decimal-representation).
