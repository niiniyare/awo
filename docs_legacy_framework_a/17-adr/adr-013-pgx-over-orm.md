# ADR-013: pgx Over ORM for Database Access

**Status**: Accepted | **Stability**: Frozen

---

## Context

Awo's Store Layer must:
1. Support PostgreSQL RLS (`set_tenant_context()` stored procedure)
2. Support `numeric(20,4)` for currency — mapped to `decimal.Decimal`
3. Support JSONB column queries with GIN index hints
4. Not leak SQL into the Domain Layer
5. Be testable via the `EntityRepository` interface (mocked in unit tests)

The choice of database driver/ORM affects all five requirements.

---

## Decision

Use **pgx v5** (`github.com/jackc/pgx/v5`) as the PostgreSQL driver. Do not use a Go ORM (GORM, Ent, sqlc with ORM patterns, Bun, etc.).

The `EntityRepository` interface is implemented by the Store Layer using pgx directly. Module authors never call pgx — they call `EntityRepository` methods which internally use pgx.

---

## Why Not GORM

GORM is the most popular Go ORM. Rejected for:

1. **`decimal.Decimal` support**: GORM has no native `decimal.Decimal` type. Requires custom Scanner/Valuer — complex and error-prone.

2. **RLS stored procedure call**: GORM has no native mechanism to call `set_tenant_context($1)` before every transaction. Hooks exist (`BeforeCreate` etc.) but they run after the connection is obtained from the pool, and PgBouncer transaction mode means `set_tenant_context` must be called at the start of every transaction, not just creates.

3. **`WHERE tenant_id = ?` leakage**: GORM scopes look like the right solution but require module authors to remember to apply them. Awo's design moves this concern to the DB (RLS) and the interface (no tenant_id in any EntityRepository method).

4. **JSONB queries**: GORM has poor JSONB support for complex queries (e.g., `data->>'field' = $1`). The Filter DSL generates these queries directly.

5. **Type switching on errors**: GORM returns `gorm.ErrRecordNotFound` as a sentinel value — type-switching on errors, which conflicts with Awo's `errors.As` error chain requirement.

### Why Not sqlc

sqlc generates type-safe Go code from SQL queries. Good for fixed queries; poor for Awo's use case:
- The Filter DSL generates queries at runtime from user-supplied predicates — not fixed at compile time
- JSONB field paths in custom entity queries are determined by tenant schema configuration — not known at compile time
- Dynamic `ORDER BY` and `LIMIT`/`OFFSET` (cursor pagination) are difficult to model in sqlc

### Why pgx Directly

- First-class `decimal.Decimal` support via `pgx` type registration
- Direct `conn.Exec("SELECT set_tenant_context($1)", tenantID)` for RLS setup
- `pgxpool.Pool` with `BeforeAcquire` callback for automatic `set_tenant_context` on connection acquire
- Full `PgError` access for structured error handling (error code `23505` for unique violations, etc.)
- No magic — SQL generated by the Store Layer is readable and debuggable

---

## Implementation Pattern

The Store Layer wraps pgx in the `EntityRepository` interface implementation:

```go
// framework/store/pg_entity_repository.go

type pgEntityRepository[T entity.Entity] struct {
    pool     *pgxpool.Pool
    compiled *kernel.CompiledSchema
}

func (r *pgEntityRepository[T]) Get(ctx context.Context, id uuid.UUID) (T, error) {
    conn, err := r.pool.Acquire(ctx)
    if err != nil { return zero[T](), err }
    defer conn.Release()

    // RLS context is set by BeforeAcquire hook on the pool — not here
    row := conn.QueryRow(ctx,
        fmt.Sprintf("SELECT %s FROM %s WHERE id = $1",
            r.compiled.SelectColumns(),
            r.compiled.TableName(),
        ),
        id,
    )
    return r.scan(row)
}
```

The `BeforeAcquire` callback on `pgxpool.Pool` calls `set_tenant_context` for every connection before it is handed to application code:

```go
pool, err := pgxpool.NewWithConfig(ctx, &pgxpool.Config{
    ConnConfig: connConfig,
    BeforeAcquire: func(ctx context.Context, conn *pgx.Conn) bool {
        tenantID := tenant.IDFromContext(ctx)
        if tenantID == uuid.Nil {
            return false  // reject connection if no tenant context
        }
        _, err := conn.Exec(ctx, "SELECT set_tenant_context($1)", tenantID)
        return err == nil
    },
})
```

This ensures RLS is always active before any query runs — module code cannot forget to call `set_tenant_context`.

---

## Consequences

### Positive

- Full control over SQL generation — no ORM magic to debug
- `decimal.Decimal` works natively
- RLS setup via `BeforeAcquire` is invisible to module code — cannot be forgotten
- Structured error handling via `pgconn.PgError.Code`
- The `EntityRepository` interface fully decouples module code from pgx

### Negative

- More Store Layer boilerplate than an ORM would require
- Dynamic SQL generation for Filter DSL requires careful parameterization to prevent SQL injection (enforced by the Filter-to-SQL compiler in the Store Layer)
- Migrations must be written manually (no ORM auto-migration — which is intentional per LAW rules)
