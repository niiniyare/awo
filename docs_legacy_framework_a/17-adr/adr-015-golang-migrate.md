# ADR-015: golang-migrate for Schema Migrations

**Status**: Accepted | **Stability**: Frozen

---

## Context

Awo requires database schema migrations with:
- Explicit `.up.sql` and `.down.sql` files (reviewable by humans)
- No auto-migration (schema changes must be deliberate and reviewed)
- Dirty state detection (fail fast on partially-applied migration)
- CLI and programmatic execution (run in CI and from Kubernetes Job)
- Multi-developer team (14-digit Unix timestamp ordering, not sequential)

---

## Decision

Use **golang-migrate** (`github.com/golang-migrate/migrate/v4`) with the PostgreSQL driver and file source driver.

Migration files are plain SQL:

```
db/migration/
    20241215143022_create_finance_invoice.up.sql
    20241215143022_create_finance_invoice.down.sql
```

`schema_migrations` table tracks applied versions. Dirty state (`dirty = true`) indicates a partially-applied migration — the migration runner refuses to proceed until the dirty version is resolved.

---

## Why SQL Files (Not Go Code)

Several Go migration libraries allow writing migrations in Go functions. Rejected:

1. **SQL migrations are reviewable by non-Go developers** (database architects, DBAs, security reviewers)
2. **SQL migrations are directly executable** for hotfix scenarios without running the full Go binary
3. **SQL migrations are unambiguous** — the exact SQL that runs is in the file, not generated by code at runtime
4. **No ORM dependency** — SQL migrations don't depend on GORM or any other ORM's schema generation

### Why golang-migrate Over goose or atlas

| Feature | golang-migrate | goose | atlas |
|---|---|---|---|
| Plain SQL files | Yes | Yes | Yes |
| Go migration option | No | Yes (but we don't need it) | Yes |
| Dirty state detection | Yes | Yes | Yes |
| Multiple source types | Yes (file, S3, go-bindata) | File only | Various |
| Docker-embedded | Yes (standalone binary) | Binary needed | Binary needed |
| Active maintenance | Yes | Yes | Yes |

golang-migrate's standalone Docker image allows running migrations in a Kubernetes Init Container without bundling the migration runner into the application image.

---

## Why `down.sql` Is Required

All migrations MUST have a corresponding `.down.sql`. Reasons:

1. **Staging rollback**: deploying to staging and discovering an error requires rolling back the migration
2. **Documentation**: the down migration documents what the up migration actually changed — a valuable constraint when writing migrations
3. **Completeness**: incomplete migrations (no down) suggest the author hasn't thought through the reversal

Down migrations are not used in production rollback (see Upgrade Guide — rolling back app code does not roll back migrations). They are used only in staging and development.

---

## Migration File Naming

Format: `{14-digit-unix-timestamp}_{description}.up.sql`

```bash
# Generate timestamp
date +%Y%m%d%H%M%S
# 20241215143022
```

14-digit timestamps (not sequential integers) allow multiple developers to write migrations in parallel without numbering conflicts. Migrations are applied in timestamp order.

Description slugs use lowercase snake_case: `create_finance_invoice`, `add_status_index_to_invoice`, `alter_contact_add_industry_field`.

---

## Consequences

### Positive

- Plain SQL: reviewable, auditable, executable independently
- Dirty state detection prevents partial-schema deployments
- Down migrations enforce thoughtful migration authoring
- Kubernetes Job pattern keeps migrations separate from application process

### Negative

- No automatic schema generation from struct tags (intentional — auto-migration was explicitly rejected in framework design)
- Developers must write SQL by hand — requires PostgreSQL knowledge
- Down migrations add authoring overhead (acceptable trade-off for safety)
